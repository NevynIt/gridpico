## Recovery and release

The bench uses Waveshare RP2040-Zero, native USB to `rpi0`, and a separately powered PIO USB hub with GP14 D+, GP15 D−, common ground and breakout VBUS open. The connected bridge identifies the APC Key 25 mk2 and MicroFreak. This baseline establishes the nominated setup before Gridpico is run.

Use the selected upstream USB path and exact current app/ROM observations. On the current bridge, assert CDC DTR deliberately and send the complete ASCII line `BOOTSEL` plus LF. Observe the CDC detach and the RP2040 ROM at the same physical connection, then return to the exact original application. Repeat with no dependency on the PIO host task. Retain two independently verified full flash reads with identical length and SHA-256, plus the known-good backup for rollback. Actual ROM and CDC return matter more than any textual acknowledgement. [Pinned bridge BOOTSEL implementation](https://github.com/NevynIt/rpico-bridge/blob/36c61af1e03c799b60c250dd41263a174b5ee5f4/firmware/cdc_bench.c#L48-L66) · [picotool 2.2.0](https://github.com/raspberrypi/picotool/blob/2.2.0/README.md)

Build `gridpico_rp2040_recovery` as a standalone Pico SDK `no_flash` target under `platform/rp2040`, with the native device controller first. Record board, SDK, TinyUSB, compiler and dependency versions and the exact ELF and UF2 digests. Require every nonempty ELF V/P `PT_LOAD` memory span to lie in `0x20000000` through `0x20041fff`. Require file-backed spans, execute entry and all written UF2 blocks to lie in the main SRAM region through `0x2003ffff`. Review for flash-writing behavior and stage only the approved RAM ELF for Pi execution. RP2040 PICOBOOT supports RAM and flash ranges. Its normal write command does not arm watchdog peripheral registers. [RP2040 boot ROM](https://github.com/raspberrypi/pico-bootrom-rp2040/blob/ef22cd8ede5bc007f81d7f2416b48db90f313434/bootrom/async_task.c#L144-L193)

The private recovery probe uses `1209:0001`, product `Gridpico Recovery Probe`, `bcdDevice` `0102` and CDC control interface `0` with data interface `1`. Omit iSerial in a `no_flash` build. Correlate by the exact physical USB path, observed descriptor and reviewed app/ROM transition. That VID/PID is reserved for private testing. On DTR, the probe emits `Gridpico RP2040 recovery` plus LF. A complete `BOOTSEL` LF line replies `OK BOOTSEL` LF, allows bounded native USB service for about 100 ms, and calls the SDK ROM reset. Preserve this command in the full target before and during PIO host startup. Ordinary serial opens at 115200 8N1 with no flow control and no implicit recovery trigger. [Test PID terms](https://pid.codes/1209/0001/) · [RP2040 ROM reset](https://www.raspberrypi.com/documentation/pico-sdk/runtime.html)

Arm a watchdog as early as possible before USB and application startup. A separate reviewed RAM watchdog fixture deliberately stops feeding only after visible readiness. BootSEL from the running probe must return to ROM. Post-arm starvation must return to the untouched bridge and allow its cooperative CDC recovery again. A normal watchdog restart and explicit ROM entry are different checks. The earliest startup instructions can still fail before the watchdog is armed. The present direct Pi root-port connection has no verified independent MCU reset. The exact guarded RAM run requires its own approval with that residual risk. Full flash replacement requires a separately demonstrated Pi-controlled recovery when the application never reaches CDC or watchdog arming. A USB link reset or unmeasured VBUS transition does not establish such recovery.

The bench observed two cooperative bridge recovery cycles and retained matching verified 2 MiB reads. HAL then used Pi picotool `2.1.1` to verify and run the exact `dbbb0729` recovery ELF in SRAM. The same upstream USB path returned through probe CDC, ROM and the original bridge. The original full flash still matched the backup and both downstream instruments re-enumerated. This verifies the probe's deliberate CDC recovery.

Independent review verified post-arm starvation on the SRAM watchdog probe, ELF SHA-256 `c12ecd4a39899d71b189a3aa3673ed25a41946847c0801db264cf8650dd1b962`. The probe produced its DTR readiness banner. The host sent no command to the probe after that. The kernel observed the original bridge enumerate directly on the same `1-1` USB path after the probe disconnected. The interval between the probe and bridge USB identity reports was 3.236 seconds. The watchdog's exact latency was unmeasured. A separate CDC BOOTSEL command to the returned bridge entered ROM for a full 2 MiB comparison against the backup. The flash matched, and the bridge and both downstream devices returned. Recovery from a failure before watchdog arming remains unverified. Full flash replacement, full SRAM routing and authenticated CDC retain their separate gates.

## Standalone firmware route

Use the same production Session/control, Graph and APC protocol code on Pico. The first hardware proof runs an ordinary managed route from the physical APC keybed to the selected MicroFreak USB MIDI input on the PIO host hub. The Pi can read control or evidence over native USB. Musical delivery takes place on Pico through the PIO host controller. During the proof leave Pi MIDI forwarding inactive and verify the physical route independently of any browser or relay. The source route and both USB backends remain bounded by the measured Pico profile and reserved release capacity.

The first full test firmware uses private `1209:0001`, product `Gridpico RP2040 Router`, `bcdDevice` `0103`, native CDC control/data interfaces `0` and `1`, and native MIDI AudioControl/MIDIStreaming interfaces `2` and `3`. Its RAM build omits iSerial. It exposes two native USB MIDI cable pairs and CDC. Wider endpoints, normal release identity and the read-only drive have separate target gates.

| Native cable | Computer → Pico | Pico → computer |
| --- | --- | --- |
| `0` | Managed Web APC Keybed ingress | Managed physical APC keybed export for a selected synth or observer |
| `1` | Web APC Panel ingress to the production frontend | Committed APC LED feedback |

On the hub the physical APC keybed and panel use their separate USB MIDI ports. The physical Panel and Web Panel each own their held edges and submit commands to the same Session. Give the physical and browser LED receivers independent delivery and refresh state. Pad `00` toggles only the physical APC → MicroFreak branch. Mirror the authoritative pad state to both receivers on attach and change as `96 00 15` for Active and `96 00 00` otherwise. CLI readback distinguishes Pending and Off. Start with desired physical keybed → MicroFreak, physical keybed → native export, and native keybed → MicroFreak enabled. Keep their lifetimes independent. Add no native input-to-native output echo. A Web peer fault cannot retire the physical APC or make its feedback stale.

Compare exact Note On and Off, route readback, scoped held-note release and both LED outputs. Distinguish firmware/adapter admission, PIO host transfer completion and actual destination behavior. USB transfer completion is evidence at the USB endpoint. Actual physical APC key presses, visible LEDs and MicroFreak response require an observed instrument or user input separate from transfer evidence. The same distinction applies to browser synth PCM and speaker output. A synthetic stimulus can verify its own path only.

## Dedicated Pico WSS service

The optional service is separate from the Pi router, its LAN Origin grant, recorder and existing WSS service. In the nominated candidate use `https://192.168.0.223:19445` with a matching IP SAN. Require exact Host and same Origin, the selected private interface, normal TLS chain verification and an enrolled mutual-TLS leaf. Keep distinct Pico MIDI Tools and Pico CDC Maintenance leaf allowlists. The maintenance leaf gains Pico CDC only. Provide no alternate Origin, plain listener, remote flash action, or shell command endpoint. The ordinary Pi `/serial` remains loopback-only over the existing trusted operator path.

Run `node connections/pico-host.js CONFIG CDC_HELPER MIDI_HELPER` with private operator-supplied files outside the checkout. The config selects `address`, `port`, `origin`, `interface`, `certificate`, `key`, `clientCA`, `midiClientFingerprints`, `maintenanceClientFingerprints` and `target`. The two fingerprint sets are disjoint lowercase SHA-256 leaf enrollments. `target` is the absolute HAL selector path. Absolute helper paths come from the approved launcher. Expose the Pico Home, APC, FM and MIDI File tools to the MIDI grant. Expose `/pico-cdc/` and WSS `/cdc` to the maintenance grant. Admit one CDC session for the selected endpoint. The opaque transcript can carry the firmware's CDC commands including cooperative BOOTSEL for that enrolled maintenance operator. A planned update retires the relay session before the Pi's maintenance procedure takes the tty.

The selector fields are `mode`, `usbPath`, `vid`, `pid`, `bcdDevice`, `product`, `serial`, `cdcInterface` and `midiInterface`. Match topology, exact four-digit lowercase hex identifiers, product and native interface indices. `usb-serial` mode requires an exact real serial. Explicit `ram-bench` mode permits `serial: null` only for the reviewed image on the nominated physical path. HAL correlates actual tty and ALSA client and cable handles to that selected device and direction. Display names, tty number and ALSA address alone do not establish identity. Reject missing or ambiguous matches. The maintenance view distinguishes the configured target from a connected target. An accepted upgrade means HAL has opened the verified endpoint.

| WSS slot | Direction from browser | Selected native path |
| --- | --- | --- |
| `/midi/1` | Send | Keybed, computer → Pico cable `0` |
| `/midi/2` | Send | Panel, computer → Pico cable `1` |
| `/midi/3` | Receive | LED feedback, Pico → computer cable `1` |
| `/midi/5` | Receive | Physical keybed export, Pico → computer cable `0` |

Verify the cable mapping on actual device/ALSA handles with asymmetric traffic before publication. The Pi service is a USB transport bridge for these roles. It does not run another musical graph. A same-origin browser synth selects `5`. A Web APC, optional laptop Web MIDI keybed bridge or [MIDI File player](midi-file.md) uses the exclusive managed send `1`. A local Web MIDI bridge explicitly chooses its physical input and forwards only the admitted notes. The hardware Panel/LED path continues independently. Keep existing three-byte MIDI WebSocket framing and actual per-role admission.

HAL owns the native endpoint helpers, identity validation, termios, DTR and transfer outcomes. Launch the CDC helper with `TARGET` and a MIDI helper with `TARGET SLOT` for each admitted directional binding. Use a private status pipe on FD `3` with `ready` LF after verified open, then admit the WS. Standard input and output carry opaque CDC bytes or contiguous three-byte MIDI messages. Pipe and WebSocket frame boundaries are independent. CDC frames carry 1–256 bytes with 8 KiB per-direction queues. Bound each MIDI binding to 64 queued frames plus one in flight. Use a five-second I/O stall deadline and one peer per role. Retirement on loss, overload or reset stops writes, drops stale callbacks and releases the exact native attachment. Rebind only after explicit fresh selection and verification. Do not replay queued events.

On a WSS input retirement with USB still mounted, the bridge drains only the note or panel releases owed by that binding to the verified cable. HAL tracks verified native submissions and distinguishes ambiguous outcomes. Keep the role reserved until bounded cleanup finishes. On inability to verify cleanup after native or helper loss, block fresh use of the affected role until verified recovery. Firmware still owns native USB loss cleanup and all physical-source note lifetime. Process death with the USB interface still mounted has a separate recovery gate. Preserve the Pi router's existing recorder, trusted LAN and SSH workflow throughout.
