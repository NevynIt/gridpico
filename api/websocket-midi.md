## Cross-host deployment and admission

- Start the network listener only with an explicit non-loopback IPv4 address, TCP port `1–65535` and canonical `https://` origin. Bind the configured address rather than a wildcard. The origin's effective port matches the listener. Include a nondefault port in the origin and leave its path, query and fragment empty. The origin's authority is also the expected `Host`. Use direct HTTPS and WSS termination with TLS 1.2 or later. Both browser and native clients validate a server certificate chain and a certificate name matching the configured origin. Treat direct TLS as the deployment boundary. [WebSocket upgrade](https://www.rfc-editor.org/rfc/rfc6455/) · [Node TLS](https://nodejs.org/api/tls.html)
- Require mutual TLS. The operator supplies server certificate and key paths, the trusted client CA, an explicit allowlist of SHA-256 client leaf certificate fingerprints, and the directional MIDI port IDs published on this listener. Store configuration and private keys outside the repository and served paths. Canonical fingerprints are 64 lowercase hex digits. Check both certificate-chain verification and enrolled leaf identity before serving content or upgrading a socket. All enrolled clients can use the explicitly published ports in this profile. Use a listener restart to apply credential or port changes and retire the associated connections. [Node TLS peer certificate and server options](https://nodejs.org/api/tls.html)
- Check the configured `Host` for every request and the exact configured HTTPS `Origin` for each WebSocket upgrade. Native clients supply that same `Origin`. Reject missing, `null` and unapproved origins. Validate client identity independently of origin. The authenticated origin serves the Web APC and Diagnostics MIDI controls, FM when installed, and the scripts they need. The browser uses its TLS client certificate and opens a same-origin `wss://` socket. Native clients use their enrolled certificate with a standard WebSocket library. [Browser WebSocket API](https://websockets.spec.whatwg.org/)
- The cross-host HTTP surface serves those static pages and admits `/midi/<port-id>` upgrades for published ports only. Diagnostics serial controls are available through its local profiles. `/serial` on the cross-host listener returns HTTP `404` before any runtime dispatch, including requests by an enrolled peer. Invalid or missing cross-host configuration leaves its listener disabled and reports a local startup error. Direct-file Web MIDI and Web Serial use the separate offline profiles.

## Shared routing and binding lifetime

Use the existing directional `/midi/<port-id>` binding and one complete three-byte MIDI message per binary WebSocket message. A successful upgrade means the production runtime accepted the binding. The listener validates authentication, origin and port publication before requesting a runtime bind. The publication list gives each unique port ID an expected graph direction (`in` or `out`). Treat that direction as an admission assertion. Read the actual direction, limit and generation from the private runtime reply. A mismatch rejects the upgrade and retires the consumed binding without forwarding staged MIDI. Route selection, status and inventory stay on the local serial CLI. [MIDI bytes and queue limits](local-router.md#loopback-transport)

Assembly supplies one persistent production router to the loopback and cross-host listeners. They share registered ports, one live binding per direction, one generation sequence for each port and the same serialized dispatch and cleanup. Changing listeners does not duplicate a route or create a new generation while the old binding is live. Managed note accounting, exact Raw bytes, APC feedback restore and independent serial backpressure use the local router contract. Connections owns admission, HTTPS/WSS resources and the binding lifetime. Scope faults to the affected connection.

On cross-host sockets, send standard WebSocket Ping every five seconds and require the matching Pong within five seconds. A missed deadline retires that binding and initiates the same scoped note cleanup or APC feedback restore as ordinary loss. A fresh authorized connection uses the next verified generation and waits for fresh input. Track local adapter acceptance and actual receipt separately. Keep the existing input/output limits and reader and dispatch deadlines. [WebSocket Ping and Pong](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.5.2)
