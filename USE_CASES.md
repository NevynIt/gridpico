# Gridpico operator workflows

The product journeys below are a first concept for review. Strategist accepted the three detailed repair workflows that follow them. The immediate priority is a visible routed LED result on the canonical local launch, followed by editing a named route and switching servers. The detailed repair workflows describe intended behavior. Browser permissions still need verification. [Product brief](PRODUCT_BRIEF.md) · [Architecture](ARCHITECTURE.md)

## Operator journeys

Visual references: [browser hierarchy and LED workflow](design/visuals/operator-workflows.png) · [one MIDI phrase on two surfaces](design/visuals/sequence-surfaces.svg).

Use the browser to identify equipment, configure named routes and diagnose a signal path. At the instrument, the player should be able to leave the computer behind and recognize the same setup from the APC’s pads. Web APC lets someone rehearse those gestures with a pointer, keyboard or touch. The following index distinguishes the product direction from the verified behavior of a particular profile. ### Browser structure and appearance

Keep a quiet, high-contrast work area with stable headings, readable port names and one prominent next action per task. Keep the connected router’s identity in a consistent position. Editing the address leaves the current identity visible until switching begins. On Home group Web APC, Routing and Diagnostics as tools, Recordings as a capability of the recording host, and optional instruments as separately deployed destinations. Keep unavailable tools discoverable with a reason and an actionable recovery. On supported direct-file Pico setups, start at the read-only drive’s Home and choose the local MIDI or serial device through the browser. Mounted-drive hardware and permissions remain target-specific gates.

Use the same names in navigation, action labels and evidence. Reserve green/amber route feedback for committed Active/Pending in Patch. A checked managed route can be Pending. Browser text, headers and focus identify the state when color alone is ambiguous. On narrow screens put server, primary action and result together and keep wide matrices scrollable. Preserve the frozen local LED flow below. The written workflows govern any illustrative differences in either concept sheet; acceptance uses observed readability and behavior.

### Prepare and play a set

At setup, choose the router and find the source by device and directional port name. For example, prepare a P-95 part for a MicroFreak destination when those ports are registered; a second output on the same row can feed a receiving instrument or Monitor. Confirm each branch independently. Pending prompts the operator to check attachment. An ambiguous returning device requires identification before playing; a familiar display name alone cannot confirm it. A connected desktop profile and a stage rig have separate hardware evidence.

For the intended computer-free set, leave the powered router, physical controller and receiving instruments connected. Play and release a phrase. The APC’s 25-key keybed sends musical MIDI into the graph. Its panel controls use the APC frontend and its LEDs show returned state. In the documented passive Patch viewport, each of five rows is a source and each of eight columns a destination. Hold Shift and press a labeled arrow on the first four Clip Stop buttons to pan one row or column. A dark cell can be Off or unmapped; amber is enabled/Pending, green Active. A pad press here leaves routes intact. The separate editable Patch profile supports a deliberate mapped-pad toggle. Check the profile before interpreting the gesture. Keep device color preferences distinct from branch status. The simulated APC preserves the same geometry and MIDI semantics and can add a text description for the focused pad. Confirm orientation, readability under stage light and physical attach/release behavior on the nominated hardware before claiming standalone acceptance. [APC viewport](api/routing.md#apc-viewport) · [Akai mapping and Patch profile](api/patchbay-controls.md#production-patch-surface)

### Follow a note and record a take

If the player hears silence, first confirm the connected router and branch in Routing. On a supported endpoint select MIDI Log’s receiving port in Diagnostics, play a fresh note and release it. Look for both received events and the expected transformed pitch. Then enable Monitor audio explicitly on its own bound input and check channel, mute and volume. A log receipt isolates delivery to Log; listening checks a separate receiving branch. For panel feedback trouble use the one-action LED workflow below.

For a Pi take, open **Recordings** on the recording router’s own origin. Choose **Start**, wait for **recording**, play fresh notes, release them and choose **Stop**. Wait for finalization before downloading the latest completed WAV. On failure identify the failed take and retain access to the previous completed file. This capture uses a separate receiving synth on the Pi; other instruments and browser Monitor own their own audio. Closing a browser tool releases its own inputs and voices. [Pi recorder lifecycle](api/pi-recorder.md#optional-recording)

### Play a local MIDI file

From Home open **MIDI File** (`/midi-file/`), choose a file on the laptop, then select the verified **Keybed** send role on the authenticated same-origin WSS router (port 1 on the first Pico profile). The file stays on the laptop. If another tool holds that exclusive input and occupancy is confirmed, explain how to release it there and offer **Retry**. Beside **Play** and **Stop**, show the filename, connected WSS router address, published MIDI input name and port ID, elapsed / total time and playback status. Before enabling Play, check the whole file and the selected target. Accept note-only SMF format 0 or 1 with supported tempo and metadata. For an unsupported event, identify its type and track/location. Explain file-limit or note-pairing failures before sending any MIDI. File or target selection alone sends no notes.

On Stop, connection loss, or replacement of the file or target, cancel scheduled playback. Also stop if the page is hidden, sending fails or playback falls more than 20 ms behind. Show the reason and require a fresh **Play**. Maintain a bounded record of notes owned by this playback and release them on the original binding while it is reachable. If the binding is lost, show **Disconnected · release unconfirmed**. A replacement binding starts idle and receives only a fresh Play. Playback status describes sending; downstream MIDI receipt requires observation at the destination.

The WSS MIDI input receives musical events. Pi router CLI, Pico CDC over direct Web Serial, and authenticated WSS Pico CDC are command paths. Direct USB Web MIDI is a separate local device selection. **Physical-laptop gate:** confirm the actual browser, device or router identity, selected port and downstream note/release on the nominated setup; record any access or disconnect limitation.

### Deferred sequencing on two surfaces

The first design exercise is **one MIDI track and one 16-step pattern**. Track identity, MIDI destination, enabled steps and playing position have the same meaning on both surfaces. Both translate gestures into intent for the shared Session/Sequencer and render resulting state. Musical Time owns transport and clock, sequence playback enters the ordinary MIDI graph and Projects owns durable saves. Changing surface or view should preserve musical state. Distinguish an applied edit from an acknowledged project save. These are forward design assumptions for review. [Sequencing boundary](ARCHITECTURE.md#time-and-future-sequencing)

**Physical or simulated APC.** Enter an explicitly indicated Sequence mode. For discussion, a labeled simulator mode control and a Shift + scene-button gesture on hardware select the same mode. A lit top-row track pad selects the MIDI track. In Patterns mode select its first pattern, return to Steps, try holding a step and playing a key to enter pitch. This candidate gesture crosses two existing paths: panel presses reach the APC frontend and keybed notes go directly to musical ingress. Before adopting it, decide whether the attack enters pitch or plays live. The path that takes the attack must also handle its matching release, even if Shift is released or the mode changes first. An explicit pitch control is the fallback. Use the first two rows beneath the track row for steps 1–16, left to right. Leave the remaining rows inactive in this exercise. A transport gesture starts playback; a second stops it. Decide its physical assignment against documented buttons before implementation. A steady lit cell marks a programmed step. A brief contrasting playhead indication returns to that underlying state as the clock advances. Show mode via a persistent panel indicator and browser text. Re-enter Patch to inspect routing while the sequence continues. Review the proposed Shift + scene gesture against the existing device-color gesture, and check fixed-color indicator legibility on hardware.

**Original Circuit-style simulator.** Choose the same named track from a dedicated track strip, open **Patterns**, select the pattern and use **Steps** to display a two-row phrase. Select a step, set its pitch using a labeled note control, then press a dedicated **Play** or **Stop** control. Use an independent position marker above the step to keep enabled content legible while playing. Handoff example: set step 5 on APC, open the simulator and see the same pitch on step 5 and the current transport position. Stop there and observe stopped transport back on APC. This is an original interaction study. Actual Circuit Tracks integration and control mapping require separate decisions.

| Shared state | APC feedback proposal | Circuit-style simulator proposal |
| --- | --- | --- |
| Track and pattern | Selected track pad plus mode indicator; explicit pattern selection | Named track strip and pattern selector |
| Step content and playhead | Stored step light with temporary position feedback | Enabled step and separate moving marker |
| Transport and recording input | Play state indicator; explicit arm gesture only after choosing an input | Play/Stop, named recording input and separate arm state |
| Later pattern change | Distinct queued pulse until playing selection commits | Separate queued and playing labels |

A later illustration may fill eight track selectors and four rows of eight steps. Capacity, bank selection, pattern launch timing, recording semantics and clock-loss behavior need product and architecture decisions. The first exercise implies no additional track memory, firmware commitments or active delivery work. Consider pattern queuing only once a second pattern is in scope.

## Start Gridpico and see a pad respond

Launch the parameterized `scripts/web-ui.sh` with its local default. Home names the selected server and keeps Web APC, Diagnostics, Routing and FM Instrument discoverable. Open **Diagnostics** and choose **Run LED test**. Keep a live five-row, eight-column pad surface beside the action, with pad 00 identified by its MIDI pad number. Keep CLI, Monitor, MIDI Log and advanced LED controls secondary to this first action. Preserve independent instrument deployments and their own entry points.

On **Run LED test**, claim the same-view APC Port 1 feedback receiver and wait for its live baseline. Acquire the bounded LED Sequence → LED feedback route for the run. Hold pad 00 solid green for a provisional one second from the moment green is visible, adjustable for ease of observation. Render Off visibly before ending the Raw lease. Arm restore observation before releasing the lease and keep the same receiver bound through restore. Show **Done** after observing green, Off and the complete ordered 40-pad refresh on that receiver. The refreshed surface reflects the latest committed state, which may have changed during the run. If the receiver drops or the refresh is incomplete, show **Restore unconfirmed** until a fresh attachment verifies committed feedback. Release the run’s resources on completion or abort. [Exclusive APC feedback](api/local-router.md#exclusive-apc-feedback)

A text status names each observed phase. A queued send alone reads **Sent · awaiting receiver**. Keep **Stop** available during the run. Only positive occupancy evidence warrants “LED receiver is in use. Release it in the other tool and choose Retry.” If the cause is unknown, show “Couldn’t connect to LED feedback. Check the selected server or release LED feedback in the other tool, then choose Retry.” Identify a confirmed expiry or disconnect and offer Retry when eligible. Local renderer preview, if offered, is labeled **Local preview**. The primary path takes one tab and requires no TX selection, route commands or setup in Web APC.

**Evidence.** From clean launcher entry, record the action, pad 00 before/green/off/restored in the same view, accepted routed messages and matching receiver frames (`96 00 15`, `96 00 00`), then Done. Capture confirmed occupancy and an unexplained connection failure separately. Verify that the original owner keeps its binding. [LED fixture](api/local-router.md)

## Edit a route between named ports

Open the separate **Routing** screen from Home or the persistent tool navigation. Head the matrix **Inputs / sources** down the rows and **Outputs / destinations** across the columns. Use registered names and IDs, including when names repeat. For example, **Keybed (1) → Monitor (5)** is an editable managed pair on canonical local startup. Each eligible cell names both ends, shows desired enabled as a toggle and reports committed Off, Pending or Active. For example, a checked Keybed → Monitor cell can read Pending while awaiting its sink. It stays checked when readback changes to Active. A disabled crosspoint explains its own restriction. Each port has its own availability label. Show an edit awaiting readback separately. While awaiting confirmation, retain the last confirmed value. On rejection, explain the reason beside the pair. Label Free, In use and Unavailable at the port, independently of its routes. Keep dedicated Panel and Raw ports visible outside the managed matrix.

Read-only inventory shows the known state and explains the edit restriction. Without an authorized current snapshot show **Routing unavailable** with the endpoint-specific recovery path. Never render unknown pairs as Off. The Pi trusted LAN exposes no router CLI. Browser Diagnostics can use the CLI through the SSH loopback fallback.

**Evidence.** At an authorized local endpoint, capture a real named pair before an edit, after switching it off and after returning it to its original setting. Match both axes, desired state and committed feedback to the runtime readback. Capture a read-only or unavailable case and its reason. [Routing contract](api/routing.md)

## Switch between local and Pi within one loaded tool

Use the same parameterized launcher and core web assets for both targets. Keep **Server address** and **Connect** in each tool. For the planned operator setup, start at `http://127.0.0.1:8767`, enter `http://192.168.0.223:18768` and choose Connect. These addresses identify the review setup. The launcher accepts a server parameter. Distinguish the requested address from the connected server throughout. Retire the old bindings and pending actions, silence held voices and clear stale results. Preserve the current tool and harmless display preferences. Reacquire only published roles. On rejection or release mismatch, show the target and reason, with Retry, address correction or explicit return to the previous server. Reconnecting requires fresh state.

Keep tools visible across targets. Local provides the routed LED fixture and starter Keybed routes to Monitor and Log. Current Pi publishes Keybed, Panel and LED feedback, without the sequence transmitter, Monitor, Log or browser-accessible routing CLI. Explain each unavailable action in place. Pi recording remains a same-origin operation in its existing deployment. Provide an explicit same-origin opening when required. Current Pi admission denies the laptop page’s origin. Same-document switching depends on exact-origin authorization and verification in the stock browser. If admission fails, offer to open the same tool path on the destination using the address already entered. Retain eligible display preferences and record this navigation fallback separately. The primary switch still requires a fresh, observed result within the original document.

**Evidence.** Compare served bytes for the core page and every loaded first-party asset at the same release on both hosts. In a single loaded document switch local → Pi → local, verify connected identity and a fresh supported action on each (use Web APC panel input and observed LED feedback on Pi), old bindings retired and unsupported actions explained. Record exact-origin permission or browser failures separately. [Browser roles](api/browser-midi.md) · [Pi profile](api/pi-recorder.md)

## Interaction and operator review

Use the same reading and keyboard order at desktop and narrow widths. Keep the endpoint and connection state together. At narrow widths stack the test button, status and pad surface together above secondary controls. Scroll the matrix horizontally within its region, retain row and column headers and show the focused pair's full names. Use native keyboard-operable controls, visible focus and text alongside color. Announce progress, completion and errors without moving focus. Keep targets usable at enlarged text sizes and let status wrap.

Representative lab viewports of 1280 × 800 and 390 × 844 CSS pixels at 100% zoom suffice to start work and accept the workflows demonstrated in the lab. The operator laptop provides a later regression comparison. Record its actual viewport, zoom, input method and clean-launch trace when available. Lab acceptance can proceed independently of that comparison and of human signoff on the artwork. Testing independently observes whether the operator can read the labels, complete each workflow and recognize its actual state on the pinned implementation. Pixel-perfect matching is outside the acceptance criteria. Architect owns feasibility of exact-origin discovery/admission, receiver observation and restore confirmation. Consult UI Designer first on later UI choices. Escalate unresolved product choices through Strategist. Cross-origin browser behavior remains open.
