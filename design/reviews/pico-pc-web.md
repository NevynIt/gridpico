## Topology and authority

| Operator target | Path and owner |
| --- | --- |
| **Pi router** | Browser → selected Pi WebSocket provider → Pi Session and route table. A Pi route can deliberately use a Pi-owned attached-Pico adapter as an ordinary named MIDI device. The Pi CLI is a separately authorized connection. |
| **Pico via Pi** | Browser → explicitly published target-scoped Pi relay → verified USB cable/direction on that Pico. The relay transports bytes. The Pico owns the Patchbay, forwarding, route revisions and committed feedback. The separate terminal path is verified USB CDC. |
| **Standalone Pico or Web UI** | Pico owns its PIO USB host census, routes and physical controller even with no PC session. Its native USB Device presents the computer-facing interfaces. The same browser assets can be served by Pi or a website, or supplied on the optional read-only MSC view. Where the browser grants Web MIDI or Web Serial, select the actual local endpoint explicitly. The asset location supplies no target identity or endpoint grant. |

Bind each tab to the selected router instance and, for Pico, the verified USB attachment epoch. Show **Pi router** or **Pico via Pi** with the selected device and status. One tab's route choice, reconnect or terminal selection never retargets the other. A capable server can automatically register browser MIDI pages by advertised name under scoped grants and opaque instance identity. Duplicate names can coexist. On a Pico relay, advertise available roles and admit a whole tool only when all required directions are committed. A named synth receiver needs an actual routable path on the selected target. Browser endpoint names and admission identities remain available on the PC side. The Pico can expose the shared USB cable name and receive the pipe as one routed direction. Independent client identity is not required beyond that USB boundary. [Automatic admission](../../api/browser-midi.md#automatic-page-admission) · [Pico-target UX handoff ID](#evidence-index)

## USB and client admission

- **One verified composite attachment.** Associate MIDI and CDC through the same verified device and interfaces. Match current bus path, verified USB serial/descriptor identity, config/interface, endpoints and cable ordinals. Readiness and authorization are separate per capability. The intended native count is two computer-relative sends and two receives, represented as distinct directions with separate owners/generations. User-facing **Cable 1** (USB ordinal 0) carries general MIDI. **Cable 2** (ordinal 1) switches between general MIDI and APC/Ableton. Authorized CLI and APC UI actions should use one authoritative Pico mode transition and committed readback. Designer will propose the gesture and indication. The cutover should retire both old Cable 2 directions and fence their waiting work and completions before publishing the new role. Keep Cable 1 and CDC independent. The installed descriptors advertise both pairs, with ordinal 1 used for APC Panel/LED in the retained profile. Qualify the supported message set and actual delivery in each new Cable 2 mode, including any DAW messages beyond the current note triplets and Panel/LED path. [Pico7 descriptor evidence](#evidence-index) · [Pico role mapping](../../api/pico-target.md#normal-two-cable-keys-slice)
- **One OS owner per physical resource.** Start with one verified adapter/relay owner and one admitted writer per USB cable, direction and role, including external DAW or OS clients. If the Pi Graph adapter and a direct Pico tool need the same cable direction, a single owner must arbitrate. The smallest first policy is explicit contention and no second open. Concurrent Pi-local and Pico-targeted tabs still work when their resources are independent. Later sharing needs a defined serialized writer/eligibility policy and bounded per-client queues. Keep authorization and admission per client on the PC side, even when clients see a shared cable name on the Pico. A shared cable is one Pico ingress owner. Keep an exclusive Panel gesture owner for the first slice so competing browser or DAW clients cannot share held-edge state implicitly. For Web APC, retain separate native and physical gesture owners and per-receiver committed LED pages from the shared Pico frontend. Measure producer acceptance, USB and WS delivery, browser render and physical lamps independently. [Pico bridge roles](../../api/pico-target.md#dedicated-pico-wss-service) · [Portable LED completion and render evidence](#evidence-index)
- **Separate serial grants.** One deliberate, exclusive Pico CDC lease, with opaque bytes for the verified selected Pico. The remote client receives the admitted target's CLI authority, so enable only under the corresponding existing scoped policy. A MIDI grant, page load or endpoint selection gives no CLI authority. For intended same-PC CLI concurrency, use independent authorized sessions, parsers, format state and reply queues, with fair serialized commands and target revision guards. One stalled client retires only its session. Concurrent sessions on separate targets establish target selection. The existing single Pi serial lease and fixed WSS denial of `/serial` remain the current boundaries. [Pico CDC](../../api/pico-target.md#private-lan-pico-cdc) · [WSS and CLI evidence](#evidence-index)
- **Bound every hop.** Count directions, admitted clients, pending claims, queues and CDC sessions independently. Attempt current connected delivery. Drop new MIDI on full waiting queues, fence stale waiting work on detach/fault/rebind and leave already-issued USB/socket writes at their actual completion boundary. Never replay old input, old feedback or CLI commands. On return, use a fresh committed LED page and current route readback. Keep MIDI dispatch bounded so authorized local control can stop or remove a mistaken deliberate loop. Auto skips exact declared loopbacks. Manual route intent and end-to-end no-echo evidence stay independent. [Current-message routing](../../api/local-router.md#current-message-managed-routing) · [Peer transit](../../api/local-router.md#simultaneous-peer-transit)
