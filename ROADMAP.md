### 1. Bind independent MIDI tools to one production router

Use one host-owned, serialized production router. Attach clients independently through selectable port bindings. The existing runner-per-socket paths stay as published regression baselines. The product interfaces between independently deployed components are MIDI and the serial CLI byte stream. A reusable loopback HTTP/WebSocket adapter carries MIDI bytes for each bound port and carries serial bytes separately. Framing identifies bindings and separates the streams. The router keeps registry, capability checks, attachment generations, accepted-delivery evidence and release accounting internal. Use selected adapter or OS ports for discovery and selection, and the local router's CLI for its inventory and status.

Web APC owns rendering and control lifetimes. Select Port 0 for keybed TX and Port 1 for panel TX and LED RX, with each direction bound explicitly. Production APC interprets gestures and supplies normal committed feedback as MIDI. Diagnostics selects a MIDI output for its named LED sequences and attaches independently to the serial CLI. Monitor and visible MIDI Log each select their own ordinary MIDI input. Monitor audio, channel filtering and sound preferences stay local to its active binding. Log displays its own receipts. It can show port, timing, hex and decoded notes when applicable. An internal acceptance trace can verify router delivery to other destinations.

Use local endpoints for the hardware-free gate and the same selection model for compatible OS-presented ports where available and permitted. Before implementation, pin direction and role access, readiness, per-peer bounds, dispatch order, failure behavior and binding lifetime. Verify independent reattachment, ambiguous or unavailable ports, exact production CLI command and reply bytes, and MIDI progress while a serial reader stalls. Application Assembly owns runtime wiring. Computer connections owns transport and attachment lifecycle. [Web MIDI API](https://www.w3.org/TR/webmidi/)
