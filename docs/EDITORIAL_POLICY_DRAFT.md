# Documentation editorial policy draft

**For review by:** Strategist, Architect, Product Owner, Project Manager and UI Designer.

- Keep a small, navigable set of focused documents. Give each fact one authoritative home: product intent in `PRODUCT_BRIEF.md`, technical boundaries and contracts in `ARCHITECTURE.md` and `api/`, current scope and maturity in `ROADMAP.md`, and task details in the relevant owner-maintained module documentation.
- Keep root guidance concise and link to the authoritative detail. Cite evidence for verified behavior, with its scope and limits. For current acceptance, keep the last verified outcome, target/build, key limit, durable evidence link, and open acceptance together. Update affected documentation alongside feature changes.
- Preserve historical context in Git and referenced evidence artifacts. Before removing a superseded procedure from active guidance, check inbound links and point readers to its durable replacement or pinned Git revision. Do not duplicate facts across pages without an explicit reason.
- Module owners curate their own documentation. Documentation maintains `README.md` and `docs/`, and coordinates readability and cross-links. Project Manager coordinates cross-owner cleanup. Do not delete or broadly consolidate documentation without agreement from its owner and leadership.

This is a proposal for discussion, not an approved enforcement policy. It sets no quotas or automatic deletion rules.
